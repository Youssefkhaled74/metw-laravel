# Changes – 2026-08-02

## Courier Shipping / Delivery System (Sections 1–5 of "ملحق ملاحظات 5")

Implemented the courier request flow end-to-end: automatic request-type detection, parallel paths with per-leg courier matching, path presentation and selection, advance payments, execution start, and editable failure messages.

### New database tables
- `request_paths` — a candidate path for a request (polymorphic `pathable`: `ShipmentRequest` or `OrderItem`). Stores `type` (`RequestPathType`), `request_type` (`CourierRequestType`), `status` (`RequestPathStatus`), `legs` JSON, `total_cost`/`currency`, `failure_reason` and the lifecycle timestamps (`courier_confirmed_at`, `submitted_to_client_at`, `client_selected_at`, `execution_started_at`, `executed_at`, `failed_at`) plus `metadata`.
- `advance_payments` — advance payment for a path (polymorphic `payable`), with `submitter_type`/`submitter_id` (User or Seller), amount/currency, `status` (`AdvancePaymentStatus`), payment method/reference, `confirmed_by`/`confirmed_at`/`rejected_at`/`refunded_at`, `metadata`.

### New / extended columns
- `shipment_requests`: `request_type` (`CourierRequestType`), `is_fast_delivery`, `submitter_type`/`submitter_id`, `selected_request_path_id` (FK), `failure_text`, `paths_evaluated_at`, `execution_started_at`, `closed_at`.
- `courier_assignments`: `request_path_id` (FK) links each leg offer to its path.

### Enums
- New: `CourierRequestType` (SINGLE_PATH, DUAL_PATH, TRIPLE_PATH, FAST_DELIVERY + `paths()`), `RequestPathType` (DIRECT_SHIPPING, WAREHOUSES, BUS, FAST_DELIVERY + `legs()`), `RequestPathStatus` (MATCHING → COURIER_CONFIRMED → SUBMITTED_TO_CLIENT → CLIENT_SELECTED → EXECUTING → EXECUTED, plus FAILED / CANCELLED), `AdvancePaymentStatus` (PENDING, PAID, CONFIRMED, REJECTED, REFUNDED), `SubmitterType` (USER, SELLER).
- Extended: `ShipmentRequestStatus` (+ MATCHING, AWAITING_PATH_SELECTION, AWAITING_ADVANCE, EXECUTING, FAILED_UNAVAILABLE), `CourierAssignmentStatus` (+ CONFIRMED = the system auto-approved courier for a leg).

### Services
- `CourierRequestTypeDetector` — decides the type from the profile: intra-governorate → FAST_DELIVERY; `DIRECT_ONLY` → SINGLE_PATH; `DIRECT_AND_MULTI` + category 3 → DUAL_PATH; otherwise TRIPLE_PATH.
- `CourierDispatchService` — rewritten to create one `RequestPath` per `type->paths()` and the per-leg offers (with `request_path_id`); keeps legacy `dispatch()` and adds `dispatchPath()` for single-path re-match.
- `CourierRequestWorkflowService` — idempotent state machine:
  - `confirmReadyPaths()` → when every leg of a path has an accepted courier, auto-approves the best one per leg (`CONFIRMED`), cancels the other acceptors, computes `total_cost`, stores the confirmed couriers in metadata.
  - `failDeadPaths()` → paths with no pending/accepted/confirmed offers become FAILED.
  - `finalizePaths()` → presents all successful paths (`SUBMITTED_TO_CLIENT`) and moves the request to `AWAITING_PATH_SELECTION`; if none succeeded, closes it as `FAILED_UNAVAILABLE` with the configured failure text.
  - `finalizeOrderItem()` → for Market-app order items (no submitter) a confirmed path immediately starts execution and assigns the confirmed courier.
  - `selectPath()` → selects the path, cancels the others + pending offers; Seller approval starts execution directly, a User moves to `AWAITING_ADVANCE`.
  - `startExecution()` → path → EXECUTING, request → EXECUTING, assigns the first confirmed leg courier as representative.
- `AdvancePaymentService` — `submitForUser`/`submitForSeller`, admin `confirm` (starts execution for a User request) / `reject`; dispatches `AdvancePaymentSubmitted`.
- `CourierAssignmentService` — accept/reject/expire now evaluate the workflow; in path mode the auto-assign-next legacy action is replaced by path-level failure handling.

### Configuration (editable failure texts)
- `CourierSystemConfigService` adds `failureShippingMessage()` / `failureDeliveryMessage()` (defaults: "Shipping/Delivery service is currently unavailable according to the required … path").
- `CourierSystemConfigSeeder` now seeds `courier_failure_message_shipping` and `courier_failure_message_delivery` settings.

### API (User / Shipping app)
Under `api/v1/shipment/requests/{id}` (in `routes/api.php`):
- `GET /paths` — list the request's paths with per-leg assignments/couriers.
- `GET /tracking` — request + paths + advance payments + failure text.
- `POST /select-path` — select a presented path (`SelectRequestPathRequest`).
- `POST /pay-advance` — submit the advance payment (`PayAdvanceRequest`).

New resources: `RequestPathResource`, `CourierAssignmentResource`, `AdvancePaymentResource`; `ShipmentRequestResource` now exposes `request_type`, `is_fast_delivery`, `selected_request_path_id`, `failure_text` and lifecycle timestamps.

### Admin dashboard
- `admin/advance-payments` (list paid/confirmed/rejected) with confirm and reject actions (`AdvancePaymentController`).
- `admin/settings/courier-failure-messages` editor for the two failure texts (`CourierFailureMessageController`).
- Shipment request detail page (`show.blade.php`) now shows a "Courier paths & advance payments" card (paths, statuses, legs, costs, confirmed couriers, payments).
- Sidebar links for advance payments and courier failure messages.
- New `admin-dashboard` lang keys (EN + AR).

### Scheduling
- `App\Console\Kernel::schedule()` now runs `CourierTimeoutProcessor` every minute to auto-reject overdue offers.

### Notes
- The `Schedule` facade is not part of `Facade::defaultAliases()` in this project, so the timeout task was registered via the Console Kernel's `schedule()` instead of `routes/console.php`.
- `route:list` fails on a pre-existing unrelated bug (`VendorUrgentTaskService` requires an unresolvable `int $vendorId`); the new routes were verified by bootstrapping the app directly.
- Advance payments for Sellers are recorded but execution starts on path selection without an admin step (per Section 3).
